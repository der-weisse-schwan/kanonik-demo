What Kanonik does today

Kanonik connects specification, process model, interfaces and code in one knowledge graph – every statement with its evidence in the document. This page shows which typical tasks around a grown system Kanonik solves today, where it covers parts of them and what comes next. Every example can be followed in this demo.

In use today

TaskWhat Kanonik doesSee it in the demo
Understand the domainTerms in German and English with synonyms, broader and narrower terms, roles, business rules and processes – each with the place in the specification it comes fromReader cinema, tab Nodes

Partly covered

  • Understand the architecture: roles and systems, interfaces with messages and data elements, processes (derived from the specification and present in the code), domain model and communication between the parties. Not yet: technical dependencies between components.
  • Understand the code: services, packages, classes, methods, sent and received messages are read from Java and linked to the specification.
  • Search across all sources: search over names, synonyms, abbreviations, English names and definitions, full text of the specification, gap search by requirement, rule, system, package, class and process. On request a chat answers questions about the graph. Not yet: search by meaning and tickets as a source.
  • Contradictions and duplicates: equivalent terms are detected and merged, contradictory broader and narrower terms reported, differing senders, receivers and names shown as gaps.
  • Traceability: from the requirement via evidence, rule and test case to the class. Not yet: as a continuous matrix for export.
  • Check rules: business rules are formalised, stored in a checkable form (SHACL) and tested with generated test cases.
  • Quality of knowledge: review status per document, provenance of every statement (document, rule, language model, expert), evaluation of decisions and recall against the test oracle.

Next

  • Profile of a system on one page: systems, roles, processes, interfaces, services, gaps.
  • Impact of a change: what is affected when a requirement, rule or message changes?
  • Traceability matrix from requirement to code and test, also for export.
  • Code as part of the graph with dependencies – the basis for comparing the architecture.

Which of these questions matters most to you is best settled with your own example.
